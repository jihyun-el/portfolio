클래식 연주자를 위한 연습·커뮤니티 앱. 악보 열람과 필기, 기기 간 동기화, 인앱 결제를 Flutter·Supabase로 개발

## 출시

Flutter·Supabase로 개발한 앱을 **iOS·Android**에 출시

2025년 9월부터 2026년 7월까지 초기팀에 풀타임으로 참여해 개발총괄을 맡았습니다. 앱의 Git 커밋 기록은 2025년 12월부터 있습니다.

- **기능**: 악보 PDF 열람과 필기, MIDI 반주와 악보 커서, 녹음, 메트로놈·튜너, 악보 상점과 인앱 결제, 커뮤니티
- **구조**: 화면 → Riverpod 상태 → Repository → Supabase(PostgreSQL, RLS, Edge Functions)와 로컬 저장소
- **반주**: 서버에서 오디오를 받지 않고 기기에서 MIDI를 합성. 조옮김·배속·구간 이동이 바로 반영됨

## 필기 동기화

필기를 PDF 원본 좌표로 저장하고 페이지 단위 3-way merge로 기기 간 변경을 병합

PDF 뷰어(pdfrx)와 필기 라이브러리가 각자 확대·이동을 처리해, 확대하면 필기만 커지고 악보는 그대로였습니다. pdfrx는 확대 상태를 밖에서 제어할 수 없습니다. 네 가지 방법이 실패했습니다.

| 시도 | 결과 |
|---|---|
| 필기 판의 배경에 PDF 뷰어를 넣기 | 확대 처리가 두 겹이 돼 제스처 충돌 |
| 바깥에서 확대 영역으로 한 번 더 감싸기 | 중첩 제스처 충돌. PDF 뷰어가 터치를 먼저 가져감 |
| PDF 페이지를 이미지로 렌더링 | 페이지당 약 18MB, 확대하면 화질 저하 |
| 두 쪽의 확대 값을 직접 맞추기 | 좌표 변환이 복잡하고 프레임 드롭 |

채택한 구조는 PDF 뷰어가 페이지마다 제공하는 오버레이 자리에 필기 판을 올리는 것입니다. 필기는 PDF 원본 페이지 좌표로 저장하고, 화면 크기에 맞추는 일은 렌더링 단계가 맡습니다. 기기와 확대 배율이 달라도 필기가 악보의 같은 자리에 놓입니다.

기기 간 동기화는 곡 목록과 필기를 다르게 다뤘습니다. 곡 목록은 마지막에 쓴 쪽을 따릅니다. 필기는 문서 전체를 덮어쓰면 다른 기기에서 쓴 페이지가 사라지므로, 마지막으로 동기화한 상태를 기준으로 페이지 단위 3-way merge를 합니다. 오프라인에서 쓴 변경은 대기열에 쌓았다가 올립니다.

## 계정 경계

탈퇴 후 재가입한 계정에 이전 소유권 **133건**이 복제된 사고의 원인 세 고리를 찾아 계정 전환 경계를 차단

같은 기기에서 탈퇴하고 재가입한 계정에, 계정 생성 31초 만에 곡 소유 기록 133건이 등록됐습니다. 손으로 내려받을 수 없는 속도라 자동 동기화가 만든 것으로 보고 경로를 추적했습니다. 세 가지가 이어져 있었습니다.

1. 탈퇴 처리가 로컬 파일은 지웠지만, 곡 목록을 들고 있던 메모리 캐시는 로그아웃 뒤에도 남음
2. 첫 동기화는 서버가 비어 있고 로컬에 곡이 있으면 로컬을 서버로 올렸고, 계정이 바뀌었는지 확인하지 않음
3. 다운로드 서버 함수가 요청한 계정의 소유 여부를 확인하지 않음

첫 동기화에서 계정이 바뀐 것을 확인하면 로컬 곡 목록과 필기를 비우도록 바꾸고, 로그아웃 때 캐시와 파일을 함께 정리하는 절차를 넣었습니다. 토큰 만료처럼 로그아웃 화면을 거치지 않는 계정 종료에서도 필기 데이터를 정리합니다. 앱의 소유 기록 쓰기는 테이블에 직접 쓰지 않고 서버 함수 호출로 옮겼습니다.

## 결제 무결성

같은 결제가 두 번 들어와도 한 번만 지급되도록 DB 고유 제약과 조건부 갱신을 겹침

잔액과 소유권은 서버만 바꿉니다. 지갑 쓰기는 서버 함수(RPC, Edge Function)만 하고, 클라이언트는 응답에 실린 잔액을 표시합니다.

- **영수증 검증**: Apple은 서명된 거래 정보(JWS)의 인증서 체인을 서버에서 검증하고, Google은 Play Developer API로 조회. 영수증에 묶인 계정이 요청한 계정과 같은지 확인
- **중복 지급 방지**: 거래 테이블에 (결제 제공자, 외부 거래 ID) 고유 제약을 두고, 조건부 UPDATE가 행을 바꾼 요청만 지급. 같은 영수증이 동시에 두 번 들어오면 한 요청만 지급되고 나머지는 "이미 처리됨"을 받음
- **지급 뒤 완료 처리**: 서버 검증이 성공했을 때만 스토어에 구매 완료를 알림. 실패하면 완료하지 않아 스토어가 영수증을 다시 보내므로, 결제됐는데 지급되지 않는 경우를 막음
- **환불 회계**: 지갑을 유료, 보상, 환불 부채 세 칸으로 나눔. 사용은 보상분부터, 충전은 환불 부채를 먼저 상계. 원장은 추가만 하고 종류별 CHECK 제약으로 불변식을 검사

결제 백엔드는 운영 서버에 배포했고, 중복 지급과 환불 회계 규칙은 DB 테스트(pgTAP)로 고정했습니다.

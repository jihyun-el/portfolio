MusicXML 악보에서 12개 조의 PDF 악보·반주 MIDI·커서 좌표와 곡 해설을 만들어 앱에 공급하는 Python 배치

## 자산 변환

조판은 verovio, MIDI는 music21로 나누고, 음표 시각을 music21 기준으로 통일해 커서와 재생이 같은 시간축을 사용

곡마다 보여 줄 악보(PDF), 들려줄 반주(MIDI), 둘을 잇는 커서 좌표가 필요합니다. verovio는 조판과 음표별 좌표를 내지만 셈여림·꾸밈음을 반영한 MIDI 생성이 약하고, music21은 그런 MIDI를 만들지만 악보를 조판하지 못합니다. 조판과 좌표는 verovio에, MIDI와 조성 분석은 music21에 맡겼습니다.

도구가 둘이면 음표의 위치와 시각이 서로 다른 곳에서 나옵니다. verovio가 계산한 시각을 쓰면 music21이 만든 MIDI의 재생과 조금씩 어긋났습니다. 음표 시각은 music21의 박 위치에서 계산하고, verovio의 음표를 박 위치로 맞춰 좌표를 붙였습니다. 두 도구의 리듬 해석 차이를 흡수하도록, 박 위치 차이가 4분음표의 0.2배 안이면 같은 음표로 봅니다.

## 커서 좌표

이조한 조에서 커서가 이전 페이지로 돌아가던 문제를 마디 기준 페이지 배정으로 수정. 「마왕」 11개 조의 역행 **13~29건 → 0건**

곡 중간에 조가 바뀌는 곡을 이조하면 커서가 이전 페이지로 돌아갔습니다. 좌표 맵을 시간순으로 읽으며 페이지 번호가 줄어드는 횟수를 세어 지표로 삼았습니다. 슈베르트 「마왕」은 원래 조에서 0건, 이조한 11개 조에서 13~29건이었습니다.

조가 바뀌는 곡은 조 구간마다 따로 옮겨야 비표준 조표가 생기지 않습니다. 이 경로는 verovio의 내부 표현(MEI)을 꺼내 음표를 옮긴 뒤 다시 읽어 들입니다. 음표를 옮기지 않고 꺼냈다가 다시 읽기만 해도 역행이 11건 나와, 원인을 다시 읽은 뒤의 레이아웃 계산으로 좁혔습니다. 일부 음표가 다른 페이지에 그려지고 있었습니다.

| 시도 | 결과 |
|---|---|
| verovio에 음표가 속한 페이지를 조회 | 12~28건. 조회 값도 다른 페이지를 가리킴 |
| 페이지별 시간 범위를 벗어난 좌표를 옮기거나 제거 | 일부 조에 1~4건이 남고, 좌표가 붙은 음표가 80~93%로 감소 |
| 페이지가 줄어드는 좌표를 제거 | 0건. 좌표가 붙은 음표가 70~88%로 줄어 수십 초 동안 커서가 멈춤 |
| MusicXML에서 직접 이조 | 0건, 좌표 100%. 임시표와 조표 표기가 기존 악보와 달라짐 |

채택한 방법은 좌표를 첫 페이지 한 곳이 아니라 모든 페이지에서 모은 뒤, 마디 단위 다수결로 페이지를 정하고 박 위치가 시간순으로 늘어나도록 제약하는 것입니다. 「마왕」 12개 조와 조가 바뀌는 5곡이 모두 0건이 됐고, 음표의 좌표는 모두 남았습니다.

## 결측 처리

템포를 못 읽으면 120BPM을 채우던 기본값이 **820곡 중 674곡**에 들어가 있던 문제를, 모르는 값은 결측으로 넘기도록 수정

악보에서 템포를 읽지 못하면 MIDI 표준 기본값인 120BPM을 채우는 코드가 있었습니다. 당시 배치 820곡 중 674곡에 이 값이 들어갔고, 곡 해설을 만드는 LLM은 이를 악보에 적힌 템포로 받아 연습 안내의 전제로 썼습니다.

2026년 2월 15일에 이 처리를 고치고, 같은 형태의 기본값을 모두 찾아 없앴습니다.

- 박자 `4/4`, 마디 수 1, 조성 `C major`를 채우던 기본값 제거
- 읽지 못한 값은 빈 값으로 넘기고, LLM 프롬프트에는 "악보에 명시되지 않음"으로 전달
- 조성처럼 없으면 진행할 수 없는 값은 그 곡만 실패로 처리하고 배치는 계속 진행

## LLM 곡 해설

Gemini 처리를 사실 수집·구조화·코칭으로 나누고 코칭 항목마다 근거 필드를 요구

Gemini API는 검색 그라운딩과 구조화 출력(JSON 스키마)을 한 호출에서 함께 쓸 수 없습니다. 검색으로 곡의 사실을 모으는 호출과, 그 결과를 스키마에 맞춰 구조화하는 호출을 나눴습니다. 연습 코칭은 구조화한 분석을 입력으로 받아 세 번째 단계에서 만듭니다.

- 악보에서 계산한 박자·템포·마디 수·음역을 프롬프트에 넣어 LLM이 추정하지 않게 함
- 코칭의 연습 과제마다 근거 필드(`basis`)를 요구: 악보, 가사, 양식 중 무엇에서 나온 조언인지 명시
- 생성 뒤 규칙으로 검사: 항목 수, 연습 시간 합계(15~20분), 빈 근거. 어긋나면 경고를 기록하고 결과를 반환

## 배치 재개

verovio의 네이티브 실패를 자식 프로세스로 격리하고, 진행 기록과 결정적 ID로 중단 후 재개

verovio는 C++ 라이브러리라 내부에서 죽으면 Python 예외로 잡히지 않고 배치 프로세스가 함께 종료됩니다. 곡마다 변환을 자식 프로세스에서 실행하고, 부모가 종료 코드(SIGSEGV, SIGABRT)를 확인해 그 곡만 실패로 기록한 뒤 다음 곡으로 넘어갑니다.

수백 곡 배치는 중간에 끊깁니다. 다시 실행해도 결과가 같도록 세 가지를 겹쳤습니다.

- 곡 ID는 처음 만들 때 진행 파일에 기록하고 재실행에서 재사용
- 조별 ID는 곡 ID와 조 이름에서 UUIDv5로 계산해 실행할 때마다 같은 값
- DB 삽입은 모두 `ON CONFLICT DO NOTHING`

곡 한 건 안에서는 Gemini 호출과 자산 생성을 동시에 실행합니다.

## 회귀 기준

구조를 바꾸기 전에 4곡의 출력을 스냅샷으로 고정. 모놀리스를 9개 모듈로 나눈 뒤에도 출력 동일

2026년 6월 30일에 평면 스크립트를 패키지로 옮기고 엔진 파일 하나를 9개 모듈로 나눴습니다. 그 전에 스냅샷 비교 테스트를 먼저 커밋했습니다. 같은 입력에서 같은 출력이 나오도록 페이지 크기를 A4로, 음표 ID 생성 시드를 고정해 둔 것이 전제입니다.

| 비교 대상 | 방법 |
|---|---|
| 좌표 맵 | 페이지 수·템포·박자 정보와 음표·마디·단 좌표의 해시 |
| MIDI | 전 트랙 이벤트열(종류, 채널, 음, 세기, 시각)의 해시 |
| 12개 조 메타데이터 | 반음 수와 조 이름 |
| PDF | 바이트는 실행마다 달라 제외하고 페이지 수만 비교 |

기준 4곡은 변환 경로가 겹치지 않게 골랐습니다. 2곡은 원래 조 한 번, 2곡은 12개 조 전체를 만듭니다. 12개 조를 만드는 2곡은 조가 바뀌는 곡과 바뀌지 않는 곡이고, 둘은 이조 경로가 다릅니다. 리팩터 뒤 네 곡의 스냅샷이 모두 같았습니다.
